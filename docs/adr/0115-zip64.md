# ADR 0115: ZIP64 archives

## Status
Accepted (v0.17.0).

## Decision
`.canvast` archives and the plain ZIP of files are ordinary ZIP files (ADR 0008). They were limited to 4 GiB and 65,535 entries. Now an archive that has more entries than that, or any entry size or offset of 4 GiB or more, is written with ZIP64 records: a ZIP64 end-of-directory record and its locator, and a ZIP64 extra field (sizes, offset) on every entry, with the ordinary fields set to 0xFFFFFFFF as the format says. Smaller archives are plain ZIP, byte for byte as before. The reader follows the locator and the extra fields, bounds-checks every number (a locator pointing outside the file, or a count past what a browser can address, is refused), and reads the local headers in parallel batches, so a 66,000-entry directory opens in a moment.

**Streaming.** Nothing holds a whole archive in memory: an export is a Blob made of the originals' own Blobs (the browser keeps them on disk) and a few small headers, checksums are computed by streaming each Blob, and an import reads the directory, then verifies every entry by streaming before it writes. The practical ceiling is what the browser lets one Blob or one download be, not the format; to go beyond it, export a board or a canvas at a time.

## Not done
Compression (originals are already compressed media), a save that streams straight to a file chosen with the File System Access API (the picker needs a click, and a big export is built long after it), and an incremental backup chain (restoring a base and then its increments needs archives to be matched to what they were exported from).

## Tests
`tests/unit/zip64.test.ts` (plain archives carry no ZIP64 records, forced ZIP64 reads back with names, sizes and bytes, 66,000 entries, damaged locators refused), `tests/unit/zip.test.ts` (still green).
